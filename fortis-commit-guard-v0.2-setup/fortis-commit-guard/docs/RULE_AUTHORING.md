# Принципы создания и изменения правил Fortis Guard

Версия документа: 0.1. Дата: 2026-10-27. Статус: проект регламента.

Документ предназначен для включения в авторитетный guard-репозиторий. Текущая
рабочая заготовка доступна агенту для изменения и ещё не является защищённой
установкой. Описанные требования не следует считать уже реализованными в CI.

## 1. Приоритет и назначение проверок

- Основа допуска — обязательный security-набор, применимый к конкретному проекту.
- Архитектурные и продуктовые контракты подключаются дополнительно решением владельца.
- Отключение дополнительного набора не отключает ни одной обязательной security-проверки.
- Цель и метод независимы. Структурная, смысловая или поведенческая проверка может
  обеспечивать security-гарантию и тогда относится к обязательному набору.
- Правило описывает проверяемое свойство, например «экспорт не включает credential».
  Формулировки «ничего подозрительного» или «модель действует разумно» недостаточны.

## 2. Авторитетная версия и доступ к правилам

- Правила, профили, критические тесты, исключения и workflow утверждаются владельцем.
- Чат может читать применимые контракты и предлагать изменения в отдельном черновике.
  У него нет пути записи к действующей версии через Docker, GitHub или host-инструменты.
- Публичность guard допустима. Скрытые тесты могут храниться приватно; исполняемая
  версия в любом случае выбирается доверенной системой, независимо от кандидата.
- Копии политик, настройки линтера, комментарии отключения правил, собственные тесты
  и файлы PASS из проверяемого коммита не меняют условия доверенной проверки.
- Доверенный реестр связывает репозиторий с профилем. Кандидат не выбирает себе
  более слабый профиль, baseline, набор тестов или режим проверки.

## 3. Переиспользование без дублирования

Общий модуль реализует механизм проверки; профиль задаёт применимость и параметры
проекта; специфический контракт описывает его поведение. Пути конкретного проекта
не зашиваются в общий модуль, когда их можно выразить параметрами.

Общее правило используется повторно. Для нового проекта обычно добавляются профиль
и специфические тесты. Тест общего модуля и тест его настройки для проекта — разные
проверки: правильный механизм с неверными путями также может пропустить нарушение.

## 4. Карточка каждого правила

У нового или изменяемого правила должна быть краткая карточка:

| Поле | Что указать |
| --- | --- |
| ID и версия | Стабильное имя и версия поведения правила |
| Цель | Security, архитектура, продуктовый контракт; допускается несколько целей |
| Гарантия и причина | Какое свойство проверяем и какой риск или дефект предотвращаем |
| Применимость | Проекты, роли областей, языки и необходимые предпосылки |
| Параметры | Разрешённые возможности, пути и границы; явные значения по умолчанию |
| Метод | Структура, синтаксический анализ, анализ данных, поведенческий тест |
| Решение | Что считается нарушением, неопределённостью и ошибкой инструмента |
| Примеры и тесты | Допустимые случаи, нарушения, попытки обхода и ошибки |
| Границы | Что означает PASS этого правила и что оно не проверяет |

Карточка может быть небольшой секцией рядом с модулем. Этот документ пока не задаёт
машинный формат метаданных: его нужно выбрать при сборке общего механизма guard.

## 5. Результаты и полнота проверки

| Результат запуска | Значение для допуска |
| --- | --- |
| PASS | Все применимые обязательные проверки завершились успешно |
| FAIL | Обнаружено установленное нарушение; автоматический допуск закрыт |
| REVIEW_REQUIRED | Нужна оценка владельца; автоматический допуск закрыт |
| ERROR | Проверка не завершилась; автоматический допуск закрыт |

Отсутствие профиля, сбой анализатора, превышение лимитов, неподдерживаемый вход или
пропущенная обязательная проверка не превращаются в PASS. Неизвестная область
получает FAIL или REVIEW_REQUIRED по утверждённой политике. Если доступную область
вообще не удалось проверить, результат — ERROR.

Неприменимость правила определяется доверенным профилем и отражается в отчёте.
Итог должен показывать покрытие: что выполнено, что неприменимо, что отключено как
дополнительное и что завершилось ошибкой. Пустой список находок сам по себе не PASS.

## 6. Испытания самих правил

До включения блокирующего правила нужны контрольные примеры:

- допустимый случай, на котором правило не срабатывает;
- нарушение, которое обязательно обнаруживается;
- для security — релевантная попытка обхода, например переименование, алиас,
  перенос операции в другой файл или подмена конфигурации;
- ошибка входа или инструмента, на которой допуск остаётся закрытым.

Примеры проверяют заявленный контракт, а не повторяют внутреннюю реализацию.
Обнаруженный обход и ложное срабатывание добавляются в набор регрессионных примеров.
Проверяется также подключение правила к нужному профилю, а не только его функция.

Для security-набора нужен контроль, что отключение дополнительных архитектурных
проверок не удаляет обязательные проверки и не меняет их параметры.

## 7. Ложные срабатывания и исключения

Ложное срабатывание исправляется уточнением условия и добавлением допустимого
примера. Нельзя ради зелёного результата исключать всю папку из security-анализа,
прятать ошибку инструмента или незаметно переводить обязательное правило в отчётный режим.

Исключение хранится в guard и содержит ID правила, точную область, причину, решение
владельца и срок действия либо дату обязательного пересмотра. Истёкшее исключение
не продлевается автоматически; требуется REVIEW_REQUIRED. Исключения видны в отчёте.
Любое реальное ослабление контракта оформляется явно, даже если названо исправлением.

## 8. Идентичность проверяемого объекта

- Проверяется точный commit SHA, а не меняющееся имя ветки или рабочая директория.
- Отчёт связывает репозиторий и SHA кандидата с версиями guard, профиля и инструментов.
- Один запуск использует одну зафиксированную версию правил. Обновление guard не
  меняет смысл уже выпущенного отчёта и не создаёт новый PASS без повторной проверки.
- Доверенный потребитель результата проверяет его источник и все эти идентичности.
  Сообщение чата, произвольный JSON или stdout кандидата не являются допуском.
- Выбор старого baseline не подтверждает безопасность существующего кода.

## 9. Безопасность выполнения проверок

Статический этап читает кандидата как данные. Он не запускает его установщики,
сборку, плагины линтера или команды тестирования. Конфигурация и зависимости самих
анализаторов берутся из доверенной версии guard.

Поведенческие проверки запускают кандидата в отдельной ограниченной среде.
Критические утверждения, наблюдение и итоговое решение остаются вне его процесса.
У кандидата нет настоящих секретов, Docker socket, доступа к основной Windows
или реальным внешним сервисам; используются фиктивные данные и тестовые сервисы.
В отчёты о найденных секретах не включаются сами значения секретов.

## 10. Порядок изменения правил

1. Описать контракт, область и причину изменения. Указать, усиливается ли он,
   уточняется или ослабляется; перечислить затронутые профили.
2. Подготовить реализацию и независимые контрольные примеры. Общий механизм по
   возможности сохранить переиспользуемым.
3. Выполнить тесты затронутых модулей и профилей, затем показать различия результатов
   до и после на реальном проекте. Изменение общего механизма требует проверки всех
   использующих его профилей.
4. Владелец рассматривает изменение вместе с новыми исключениями, потерей покрытия,
   сменой инструментов и перечнем ранее запрещённых случаев, которые теперь проходят.
5. После утверждения фиксируется новая версия guard и её применение к проектам.
   До переключения продолжает действовать предыдущий утверждённый security-набор.
6. Откат также является явным решением владельца. Известный обход должен оставаться
   отражённым в ограничениях; возврат версии не делает уязвимость устранённой.

Новое экспериментальное правило можно испытывать в отчётном режиме до включения.
Эксперимент не заменяет действующие обязательные проверки и не расширяет их PASS.

## 11. Стоимость и сложность

Сначала используются простые проверки структуры и разрешённых возможностей.
Дорогие проверки запускаются для применимых проектов и областей с учётом их
зависимостей; анализ только изменённых строк не считается достаточным по умолчанию.
Изменения импортируемого кода, профиля и инструментов также могут менять результат.

Переиспользуются готовые инструменты и общие модули. Отдельная ИИ-оценка не является
обязательной основой допуска. Кеш разрешён только с ключом, учитывающим проверяемые
входы и версии правил, инструментов и параметров; несовпадение требует новой проверки.

## 12. Пример: область пассивной документации

Контракт security: в этой области допустимы документы утверждённых форматов;
исходники, исполняемые файлы, активные вставки и подключения исполняемой логики
запрещены согласно возможностям используемого потребителя документов.

Примеры кода внутри Markdown могут оставаться текстом. Это допустимо только если
потребитель не исполняет их как шаблоны или плагины. Документы-команды для ИИ имеют
отдельную роль: отсутствие программного кода не доказывает безопасность инструкций.

Если внутри documentation уже находятся приложения, профиль выделяет их в отдельные
области. Имя папки не является доказательством её пассивности. Один модуль проверки
областей может обслуживать несколько проектов с разными настройками.

## 13. Применение к текущему прототипу

Первый прототип с 41 контрольным тестом послужил исходным материалом. В устанавливаемой
версии добавлены реестр проектов, обязательный security-набор, дополнительная
архитектурная проверка и карточки модулей. Жизненный цикл исключений, полная
отчётность покрытия и поведенческие тесты приложения ещё не реализованы.
Документ задаёт требования к развитию этих механизмов.

Методические источники:

- [ESLint: тестирование правил на допустимых и запрещённых примерах](https://eslint.org/docs/latest/extend/custom-rule-tutorial).
- [GitHub: безопасность workflow и исполнения недоверенного кода](https://docs.github.com/en/actions/reference/security/secure-use).
